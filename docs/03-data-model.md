# โครงสร้างข้อมูลและกฎธุรกิจ

> **สถานะเอกสาร:** แบบจำลองเชิงแนวคิดช่วงวางแผน ไม่ใช่ schema ที่ใช้อยู่จริง ปัจจุบันรวมเรื่อง/ฉบับไว้ใน series และใช้ SQLite ดู [19 — ข้อมูลและฐานข้อมูล](19-data-and-storage.md) สำหรับ fields ตาราง และตัวอย่าง JSON ที่ตรงกับโค้ด

นี่คือแบบจำลองเชิงแนวคิด ยังไม่ใช่ schema migration ชื่อและตารางเปลี่ยนได้ แต่ต้องคงกฎธุรกิจและตรวจรับได้

## Entities

| Entity | หน้าที่และข้อมูลหลัก |
| --- | --- |
| User | auth subject, ชื่อแสดงผล, preferences |
| Work | เรื่อง/ชุด, ชื่อหลัก, ประเภท, รายชื่อผู้สร้างและบทบาท |
| Edition | ฉบับของเรื่อง: ภาษา สำนักพิมพ์ ชื่อฉบับ/รุ่น |
| Volume | เล่มภายใต้ฉบับ: ชื่อ, label เล่ม, ลำดับ, ประเภทเล่มปกติ/พิเศษ, identifier |
| BoxSet | สินค้าแบบชุดภายใต้ฉบับหรือชุดที่ระบุ พร้อม ISBN ของเซ็ตถ้ามี |
| BoxSetMember | ความสัมพันธ์ชุดกับ Volume และจำนวนต่อชุด |
| LibraryEntry | รายการของผู้ใช้ ชี้ไป Volume หรือ BoxSet อย่างใดอย่างหนึ่ง, status, quantity, ที่เก็บ, หมายเหตุ |
| Draft | ข้อมูลที่ยังไม่ยืนยัน รูป/ISBN ข้อเสนอจาก provider และสถานะงาน |
| MetadataCandidate | ข้อมูลจากภายนอกพร้อม provider, external ID, เวลาค้น, provenance ราย field |
| SyncOperation | operation ID, owner, entity, base revision, payload และผลการประมวลผล |

Work/Edition/Volume/BoxSet ที่ผู้ใช้สร้างหรือแก้ให้มี owner ก่อนในเวอร์ชันแรก ไม่เปิดให้การแก้ชื่อของคนหนึ่งกระทบอีกคน ข้อมูล provider อาจมี cache ภายในที่เซิร์ฟเวอร์ดูแล แต่ไม่ใส่ชื่อย่อ หมายเหตุ รูปส่วนตัว หรือข้อมูลครอบครองลง cache ร่วม การทำ global catalog เป็นงานภายหลัง

## Identifiers และเลขเล่ม

- Edition มี `format: physical | ebook` แยกจากภาษา/ชื่อฉบับ การครอบครองของแต่ละรูปแบบเป็นอิสระ เรื่องเดียวกันมีทั้งสองได้
- ต้นแบบเก็บ format ที่ series ซึ่งทำหน้าที่เป็นเรื่อง+ฉบับ แต่ระบบจริงย้ายไป Edition; ไม่ยัด format ลง status
- ISBN ของหนังสือเล่มกับ ebook อาจต่างกัน และ ebook ที่ไม่มี ISBN เพิ่มได้ ไม่ยืม ISBN ของเล่มกระดาษให้เอง
- prototype schema v2 กำหนด format ชัดเจน ข้อมูล v1 ที่ไม่มีตัวเลือกนี้จะ migrate เป็น physical โดยไม่เปลี่ยน ID/สถานะ/สมาชิกบ็อกซ์; สำเนาต้นฉบับจะไม่ถูกเขียนทับตอนอ่าน ย้ายเป็น v2 เมื่อผู้ใช้บันทึกครั้งถัดไป

- ใช้ ID ภายในที่สร้างฝั่ง client ได้สำหรับ draft และ operation ออฟไลน์ เช่น UUID
- ISBN เก็บเป็น string ไม่ใช่ integer เก็บ raw input และรูป normalized แยกกัน
- ISBN-10/13 ตรวจ checksum; แปลง ISBN-10 ที่ถูกต้องเป็น ISBN-13 สำหรับการเทียบเมื่อทำได้ เก็บรูปต้นฉบับด้วย
- ISBN ของบ็อกซ์ไม่เท่ากับ ISBN ของเล่มภายใน และ ISBN ไม่ใช่ primary key ของ LibraryEntry
- เล่มที่ไม่มี ISBN ใช้งานได้ ห้ามสร้างเลขให้เอง
- เก็บ `volume_label` เช่น “ภาคพิเศษ”, “0”, “1.5” และ `sort_order` แยกกัน ไม่บังคับให้ทุกเล่มเป็นจำนวนเต็ม
- ISBN ซ้ำในข้อมูลภายนอกหรือระเบียนชั่วคราวให้เป็นรายการต้องตรวจ ไม่ merge หรือลบข้อมูลผู้ใช้อัตโนมัติ

## การครอบครองและจำนวน

- LibraryEntry มี `owned`, `ordered`, `wishlist` สถานะเดียวต่อ record และ quantity เป็นจำนวนเต็มบวก
- ถ้ามีเล่มหนึ่งแล้ว 1 สำเนา และสั่งอีก 1 สำเนา ให้เป็นคนละ entry เพื่อไม่เสียสถานะใดสถานะหนึ่ง
- เปลี่ยน ordered เป็น owned เมื่อของถึง โดยไม่สร้าง entry เพิ่มซ้ำ หากรับของบางส่วนให้แยกจำนวนเป็นสอง entry อย่างตรวจสอบได้
- ผู้ใช้ยืนยันเก็บหลายสำเนาได้ การเตือน ISBN ซ้ำไม่ใช่ unique constraint ที่ห้ามมีหลายสำเนา
- draft แยกต่างหาก ไม่ใช้ status ของ LibraryEntry และไม่รวมยอดในชั้น

## บ็อกซ์และ coverage

- หนึ่ง entry ชี้ไปเซ็ตหรือเล่มเดียวด้วย constraint แบบ exactly one target
- เซ็ตสร้าง coverage ของเล่มภายในตามสมาชิกที่ยืนยันแล้ว ไม่สร้าง owned entries ของเล่มภายในซ้ำอีกชั้น
- ผลเช็กเล่มแสดงทั้ง direct holdings และ holdings ผ่านเซ็ต รวมสถานะ/จำนวนโดยไม่ double count
- จำนวนสินค้าที่ซื้อ (เซ็ต/เล่มเดี่ยว) กับจำนวนหนังสือจริงภายในให้แยก label ชัดเจน จำนวนเล่มจริงอาจไม่ทราบถ้าสมาชิกเซ็ตไม่ครบ
- เปลี่ยนสมาชิกของเซ็ตที่เคยบันทึกแล้วต้องยืนยัน เพราะมีผลต่อ coverage ห้ามให้ provider refresh เปลี่ยนเอง

## เล่มขาดและการจับคู่

- ลำดับ 1,2,4 แสดงช่องว่าง 3 ได้ แต่แยกจากข้อสรุปว่าเล่ม 3 วางขายแล้ว
- “ขาดจากชุดที่ต้องการ” ใช้รายการเล่มเป้าหมายที่ผู้ใช้ยืนยัน ไม่ใช้เลขสูงสุดทำนายอนาคต
- exact ISBN match เป็นสัญญาณซ้ำที่ชัด แต่ยังให้ตรวจ edition/target เมื่อข้อมูลขัดแย้ง
- ชื่อคล้าย ผู้เขียนตรง หรือชื่อจีน/ไทยใกล้เคียงเป็น candidate เท่านั้น ผู้ใช้เลือกเชื่อมเอง

## Provenance และวงจรชีวิต

- แยกค่าที่ผู้ใช้ยืนยันจากค่าเสนอโดย provider/AI พร้อม source และเวลาที่ดึง
- ห้าม refresh metadata เขียนทับข้อมูลที่ยืนยันแล้วโดยไม่รีวิว
- entity ที่ซิงก์ได้มี owner ID, revision, server timestamps และ tombstone สำหรับลบ
- เซิร์ฟเวอร์เป็นผู้กำหนด revision และเวลา canonical ไม่ใช้เวลาบนเครื่องตัดสินว่าใครชนะ
- export ต้องรักษาความสัมพันธ์เรื่อง/ฉบับ/เล่ม/เซ็ต สถานะ จำนวน ชื่อย่อ และหมายเหตุ พร้อม schema version
- นโยบาย retention ของ tombstone, operation และรูปเป็นการตัดสินใจที่ต้องปิดก่อน production
